# ERC-8004: 権限とRegistry状態遷移

対象はDraft仕様のcommit `503591a6e80e6e1affdd6403341e25269141f046`。
公式実装は `b9e466c250744a7e06b13dff9d3c2844ed64f825` に固定する。
原文、調査対象Solidity、上流テスト、コンパイラ設定、lockfileを
[`specs/erc8004`](../specs/erc8004/NOTICE.md) に保存した。

## 実行モデル

名前空間は `LeanForStandardization.ERC8004`。`State`はAgent、所有者、wallet、
token単位の承認、owner単位のoperator承認、feedback、validation requestを保持する。
`execute`が成功または拒否を返し、`step`が拒否時に元の状態を保つ。
`run`は逐次操作列を評価する。実ネットワーク、EVM、署名処理には依存しない。

| Registry | 今回の操作 | 今回扱わないもの |
|---|---|---|
| Identity | 登録、所有権移転、token/global承認、wallet設定・解除 | URI、metadata一般、ERC-721 callback、burn、upgrade、署名暗号処理 |
| Reputation | feedback投稿、投稿者ごとの連番、int128/decimals検査 | 撤回、response追加、集計、tag/URI/hash、Sybil判定 |
| Validation | 権限付きrequest、指定validatorのresponse、繰り返し更新 | 外部データの内容、hash計算、timestamp、集計、validatorの判断根拠 |

token単位の承認は移転時に消去する。global operator承認はownerに結び付くので、
移転先ownerが既に与えた承認は有効なままである。この違いを単一のoperator集合に
潰すと、移転後の権限について誤った結論になる。

## 証明した範囲

`Properties.lean`の8定理をLean 4.35.0でコンパイルして検証した。
`sorry`、`admit`、独自axiom、`native_decide`は使用していない。

| 定理 | 結論 | 明示した前提 |
|---|---|---|
| `transfer_clears_wallet_and_approval` | 成功した移転でwalletとtoken承認が消え、ownerが更新される | その移転の`execute`が成功する |
| `transfer_revokes_unapproved_authority` | 移転後、対象の第三者には管理権限がない | 第三者は新ownerと異なり、新ownerからglobal承認を受けていない |
| `accepted_feedback_excludes_authority` | 成功した投稿者はowner/token/global operatorでなく、数値域も妥当 | 投稿が成功する |
| `authorized_feedback_rejected` | 現在の管理者のfeedbackは拒否され、状態が変わらない | Agentが存在し、投稿者が管理権限を持つ |
| `request_requires_authority` | 成功したvalidation requestには管理権限がある | requestが成功する |
| `response_requires_designated_validator` | 成功したresponseは元requestのvalidatorによる0–100の値 | responseが成功する |
| `response_preserves_request_binding` | response更新はagent/validatorの関連付けを維持する | requestが存在し、responseが成功する |
| `rejection_preserves_state` | どの操作でも拒否時に全状態を保持しeventを出さない | `execute`が拒否する |

これらは抽象モデルの定理であり、Solidityバイトコードの正しさを証明したものではない。
Registryの整合性からfeedbackの真実性、Sybil耐性、validator判断の正しさは導けない。

## モデル選択と環境仮定

- アドレスとhashを`Nat`で抽象化する。EVMと比較する入力は非zero caller、160-bitアドレス、
  256-bit Agent ID/hashに写像可能なものに限る。整数カウンタのoverflowはモデル化しない。
- Agent IDは0から採番する。仕様は逐次採番までを規定する。0開始は固定Solidityの
  `$._lastId++`とfresh storageに合わせた選択で、上流`core.ts`の連続IDテストも読んだ。
- `approve`/`setOperator`は権限研究に必要なsubset。ERC-721の全エラー分類や自己承認の
  細則は再実装していない。token承認とglobal承認の区別・移転時のtoken承認消去は扱う。
- walletの`proofValid`は検証済みのEIP-712/ERC-1271証明に対応する外部入力。署名の
  domain、ownerへのbinding、deadline、ERC-1271 callbackの妥当性は証明しない。
- wallet変更・解除はownerまたは承認済みoperatorに許す。これはERC-721の管理委譲と
  固定実装の権限チェックに沿うモデル選択。仕様のwallet段落ではownerに言及するが、
  operatorの扱いが同段落だけで明記されているわけではない。
- 同じrequest hashの新規登録を拒否する。固定実装の一意性制約に合わせた選択で、
  仕様の「requestを識別する」という表現だけから、すべての衝突処理が決まるとはしない。
- 非zero validator、walletを要求する。walletの未設定は`none`で表し、EVMのzero addressに対応する。
- 各操作は原子的に終わる。拒否時にstateを保持する仕組みはEVMのrevertを抽象化した設計で、
  ERC-8004本文に追加のMUSTがあるかのように扱わない。
- `Event`は意味上の通知であり、Solidityの全event引数・順序を忠実に再現するABIモデルではない。
  CLIは現在、状態とaccept/rejectだけを出力する。

## 再現とテスト

```bash
lake build
lake exe model-tests
lake exe oracle erc8004 tests/erc8004/transfer-wallet.json
lake exe oracle erc8004 tests/erc8004/validation-race.json
lake exe oracle erc8004 tests/erc8004/value-cap-witness.json
```

`runTests`は移転後の古い承認、owner/token/global operatorのfeedback、decimals 18/19、
int128上下限、wallet証明拒否、request競合、response 0/100/101、移転後のresponseを検査する。
さらに11操作のalphabetについて長さ1–4の全prefix、16,104遷移を検査する。
これは有界探索であって、すべての操作列を網羅した証明ではない。

「過去のownerからのfeedbackも永久に禁止される」という強い仮説について、3操作の
alphabetで長さ0–3を短い順に探索した。最短の反例は登録→移転→旧ownerのfeedback。
[`former-owner-feedback.json`](../tests/erc8004/former-owner-feedback.json) に保存した。
これは仕様の現在権限に対する禁止を越えた仮説の反証であり、仕様の欠陥とは判定しない。

JSON入力の`operations`には`op`と`caller`、操作固有フィールドを指定する。
`feedback.value`はdecimal stringまたはJSON整数を受理し、出力では精度を保つため常に
decimal stringとする。`state.agents`、`state.feedback`、`state.validations`と、
各操作の`outcomes`を返す。構文エラーはCLI失敗、プロトコル拒否は正常なJSON結果になる。

## Solidityとの比較

固定ソースで以下を確認した。

- Identityの`_update`は移転時walletを消去。上流`core.ts`にもそのテストがある。
- Reputationは`isAuthorizedOrOwner`を使い、ownerと両種のoperatorを禁止する。
- Validationはowner/token/global operatorによるrequest、元validatorによるresponse、
  response最大100、重複request拒否、繰り返しresponseを実装する。
- `test/core.ts`の「ownerだけがrequestできる」というテスト名は、本文では未承認者の
  拒否とownerの成功を検査している。operator不許可の証拠として扱わない。
- feedbackに仕様本文で見つからない`±10^38`制限がある。入力`10^38 + 1`はint128内に
  ありモデルで成功するが、固定Solidityでは`value too large`で拒否される。
  固定環境のローカルEVMでtransactionを再現した。詳細はfindingsを参照。

コンパイラ設定はSolidity 0.8.24、Shanghai、optimizer有効/runs 200、viaIR true。
デプロイの基準は上流core testの`HardhatMinimalUUPS`→`ERC1967Proxy`→実装へupgrade
およびreinitializer(2)。独立adapterによるローカルEVM比較で、移転・自己feedback・
元ownerのfeedback・validationの4ケースが一致、数値域の1ケースが不一致となった。
各1操作の削除候補が一致することも再実行し、2操作の削除最小性を確認した。
固定条件と再現手順は[独立EVM比較](evm-comparison.md)を参照する。

## 未検証と次の優先順位

1. 実行で再現した追加数値上限の意図と、仕様が許す追加制約かどうかを人間レビューで確認する。
2. request hashの重複方針、walletを変更するoperatorの権限を明確化し、差分生成テストの範囲を広げる。
3. ERC-721 callback/reentrancy、署名の期限・owner binding、storage upgradeを別のモデル層として扱う。
4. feedback撤回・集計、validation集計を拡張する。評判の真実性を証明対象に混ぜない。

公平性・到達可能性を前提とする活性定理は今回の対象外。暗号とEVMについて証明できなかった
のではなく、抽象境界の外に置いた。証明が通らなかった定理を未証明axiomで埋めてはいない。
