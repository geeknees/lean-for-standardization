# 研究方法

## 仕様からモデルへ

可変なWeb本文をそのまま研究対象にせず、リビジョンとGitコミットを固定する。`specs/` の取得原文とハッシュ、`docs/spec-versions.md` の取得元を使って追跡する。原文の要約とLeanの対応は `docs/spec-traceability.md` に記録する。

MUST / MUST NOTはその適用前提を満たす実行に課す制約とする。SHOULDは例外を持ち得る推奨であり、採用したモデルを仕様全体の唯一の振る舞いとみなさない。MAYは選択肢を与える。大文字規範語がない要求文は「本文要求」と記録し、MUSTへ格上げしない。候補順序や時刻の扱いなどのモデル方針は別欄に置く。

実行意味論は純粋な `step` と `run`、命題は `Properties.lean`、JSON変換は `Oracle.lean` に置く。JSONの破損と、正しい形式だがプロトコルに拒否される操作を分離する。実装する前に仕様の境界と異常シナリオを選び、実行可能な期待値を置く。

## 証拠の強さ

| 証拠 | 主張できること | 主張できないこと |
|---|---|---|
| Leanのカーネルで検証した定理 | 明示した定義・仮定に対して命題が成立する | 自然言語の解釈が正しい、現実の実装が正しい |
| 決定的シナリオ／有限列探索 | 実行した入力と範囲で条件を満たした | 未探索入力や無限列に対する性質 |
| Solidity原文・既存テストの比較 | 固定ソースの条件式やテスト意図に差がある | コンパイル・デプロイ後の実動作が一致／不一致 |
| 独立EVMとの差分テスト | 固定構成と操作列で観測が一致／不一致 | 任意のEVM実行との同値性 |
| Mozilla状態機械との差分テスト | 共通のDNS・時刻・callback列で、公開出力の射影が各prefixで一致／不一致 | 実ソケット、公開APIにないTLS内部動作、仕様全体への準拠 |

反例の縮小では、失敗述語を保ちながらイベントを削除する。削除で縮まらないこと（1-minimal）と、全候補中で最短であることを区別する。手作業で候補を選ぶ場合も、短縮した列を再実行する。

実装比較では、仕様の版、同じ時刻の入出力の処理順、公開APIで観測できる範囲を先に固定する。未発行接続へのcallbackなど、削除で入力が不適格になった候補は不一致として数えない。最終状態が一致しても途中の差が消えないよう、[Mozilla比較](mozilla-comparison.md)では全prefixを記録する。

## 証明監査

`lake build` と `lake env lean LeanForStandardization.lean` で証明項を検査する。さらに `lake env lean Audit.lean` が、プロジェクト名前空間内の定義・定理の推移的な公理依存を `Lean.collectAxioms` で調べる。許可する基盤公理は `propext`、`Classical.choice`、`Quot.sound` のみ。`sorryAx`、独自公理、`native_decide`の実行結果を信頼する公理は許可しない。

文字列監査は補助であり、Leanの依存監査に置き換わらない。テスト実行はネイティブコードを利用できるが、その成功をカーネル証明と呼ばない。Leanのカーネル、標準ライブラリ、ツールチェーンと実行環境は信頼基盤に残る。任意の悪意あるLeanメタプログラムや改変されたコンパイラへのセキュリティ監査ではない。

`ruby scripts/check-audit.rb` は一時ファイルに、別名前空間の公理への依存、未完成証明、ネイティブ決定手続きの3つを注入し、監査が意図した依存名で失敗することも確認する。private定理も監査対象に含む。プロジェクトの証明ファイルにこれらの逃げ道を残さない。

## 独立性と上流への報告

Leanモデルは仕様から作り、既存実装とロジックを共有しない。ソース比較・差分テストで相違が見つかっても、モデルの誤読を先に点検する。仕様原文とソースの出典、実行結果、前提、最小列、既存議論を揃え、人間のレビュー後にのみ上流へ報告する。このプロジェクトから自動でIssueやPRを投稿しない。

参考にした研究構成は [lean4-dom](https://github.com/takahashim/lean4-dom/tree/336ca6191d9beba236d544c8dfa32502db880897) の実行モデル、性質の証明、差分テスト、仕様対応表である。本プロジェクトのモデルは独自に記述している。
